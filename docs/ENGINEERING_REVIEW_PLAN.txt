FitPilot 个性化训练与膳食协同 AI Agent
工程落地审查与完整改进方案 V1.1
1. 项目现状评价
FitPilot 当前已经不是简单的健身问答项目，而是具备以下完整雏形的垂直领域系统：
PostgreSQL 管理用户、计划、动作、食物和打卡等结构化数据；
Qdrant、BM25、Reranker 构成混合 RAG；
LangGraph 完成意图路由、风险拦截和计划生成；
训练计划和膳食计划采用“预览—确认—写入”机制；
营养数值和训练容量采用确定性代码计算；
前端支持登录、档案、记录、动作库、食物库、对话和计划管理；
已配置日志、Prometheus、Trace、健康检查、测试和基础评估。
这些设计方向总体正确，尤其是“结构化业务数据与非结构化知识分离”“LLM 不直接计算营养数值”“写操作必须确认”等原则，符合成熟 Agent 项目的工程要求。
但从工程成熟度看，当前系统仍应定位为：
功能较完整的 MVP，而不是已经可以长期稳定运行的生产级 Agent。
最主要的问题并不在页面数量或功能数量，而在于：
Agent 任务和 Trace 仍然依赖进程内存；
Agent 实际更接近“意图路由器”，缺少真正的多步骤规划与动态重规划；
训练计划和膳食计划的个性化深度不足；
RAG 缺少完整的数据治理和高级召回机制；
评估主要集中在检索指标，没有覆盖 Agent、计划、安全和业务正确性；
生产部署、备份恢复、权限控制和集中式可观测仍不完整。
2. 当前项目的主要优点
2.1 数据分层合理
当前将用户档案、训练记录、饮食记录、动作和食物存入 PostgreSQL，将指南、科普和文档存入 Qdrant 与 BM25，这是正确的架构。
结构化数据需要精确查询和事务保证，不应通过向量检索返回；非结构化知识则适合 RAG。README 中已经明确区分了两者。
2.2 计划写入具备人工确认
训练和饮食计划采用：
生成预览
→ 用户查看
→ 用户确认
→ 正式写入
这比让 Agent 直接修改用户计划安全得多，也是 Human-in-the-loop 的基础。
2.3 确定性计算边界明确
热量、宏量营养、训练容量等数据由代码计算，而不是让 LLM 自由生成。这能够显著降低数值幻觉。
2.4 已经具备基本工程设施
项目已经包含：
uv 依赖管理；
Alembic 数据库迁移；
Docker Compose 基础设施；
Prometheus；
structlog；
健康检查；
GitHub Actions；
RAG 黄金测试集；
CLI 运维命令。
因此下一阶段不需要推倒重写，而应该针对关键短板增量改进。
3. 核心不足一：Agent 还不是完整的任务型 Agent
3.1 当前问题
当前状态图基本为：
classify
→ safety / boundary / rag / personal / plan / log_hint
→ END
每个请求通常只进入一个节点执行一次，然后结束。
这更接近：
意图分类器 + 多条固定业务链路
而不是真正具有以下能力的 Agent：
根据目标拆解多个步骤；
连续调用多个工具；
根据工具结果改变后续步骤；
校验中间结果；
失败后重试或降级；
在缺少数据时主动提出补充项；
根据用户反馈重新规划。
例如用户提出：
根据我最近两周的体重、训练和饮食记录，调整下周训练计划和食谱。
完整流程应该是：
读取当前目标
→ 查询体重趋势
→ 查询训练表现
→ 查询饮食完成度
→ 计算恢复和执行情况
→ 判断问题原因
→ 调整训练
→ 重新计算营养目标
→ 调整食谱
→ 业务约束校验
→ 风险检查
→ 生成修改对比
→ 等待用户确认
→ 写入新版本
当前 README 中的 plan 节点尚未体现这种多步骤闭环。
3.2 改进方案
建立两级 Agent 架构。
简单任务使用确定性路由
例如：
查询一种食物；
查询一个动作；
查看本周训练次数；
普通知识问答。
这类请求不需要复杂 Agent，直接进入固定流程，减少延迟和 Token 消耗。
复杂任务使用 Planner–Executor 工作流
建议状态图改为：
START
  ↓
安全与权限检查
  ↓
意图与复杂度判断
  ├─ 简单任务 → 固定链路
  └─ 复杂任务
          ↓
      Task Planner
          ↓
      Tool Executor
          ↓
      Result Validator
          ↓
      是否满足目标？
       ├─ 否 → Replan
       └─ 是 → Safety Gate
                    ↓
              Human Approval
                    ↓
               Commit / END
Agent State 至少应包含：
task_id
user_id
session_id
intent
goal
constraints
required_data
execution_plan
current_step
tool_results
validation_errors
risk_level
approval_status
plan_version
retry_count
3.3 工具调用治理
每个工具必须具有：
Pydantic 输入模型；
明确的输出模型；
用户权限检查；
参数范围校验；
超时；
重试次数；
幂等键；
错误码；
审计记录。
工具应明确分为：
只读工具
计算工具
预览工具
写入工具
回滚工具
例如：
get_training_history
calculate_weekly_volume
preview_training_adjustment
validate_training_plan
commit_training_plan
rollback_training_plan
不能让一个 update_plan 工具同时负责分析、生成、校验和写库。
4. 核心不足二：Agent 任务和 Trace 不持久化
README 明确指出：
Agent 任务事件保存在进程内存；
Trace 保存在长度为 200 的内存队列；
服务重启后数据会丢失。
这是当前最重要的工程短板之一。
4.1 可能导致的问题
服务重启后 SSE 任务无法继续；
用户刷新页面后无法恢复任务状态；
多进程部署后，不同实例看不到同一个任务；
Trace 无法长期分析；
无法复现一次错误的 Agent 决策；
无法做 Agent 成功率和工具轨迹统计。
4.2 改进方案
将任务状态存入 PostgreSQL
建议建立：
agent_tasks
agent_task_steps
agent_events
agent_tool_calls
agent_approvals
agent_failures
agent_tasks 保存：
task_id
user_id
status
intent
request_payload
result_payload
current_step
created_at
started_at
completed_at
error_code
使用 Redis 管理实时事件
Redis 用于：
SSE 事件发布；
任务进度缓存；
短期锁；
幂等键；
Agent 会话状态；
限流。
使用后台 Worker
建议增加独立 Worker：
FastAPI
→ 创建任务
→ Redis 队列
→ Worker 执行 LangGraph
→ PostgreSQL 持久化状态
→ Redis 发布 SSE 事件
可以使用：
Celery；
Dramatiq；
RQ；
ARQ。
项目当前规模下，ARQ、Dramatiq 或 Celery 均可，重点是不能继续依赖 FastAPI 进程内后台任务。
LangGraph 持久化
为 LangGraph 配置 Checkpointer，使任务能够：
暂停；
等待用户确认；
服务重启后继续；
从失败节点恢复；
查看历史状态。
5. 核心不足三：训练计划的个性化程度不足
5.1 当前问题
README 描述的计划生成方式主要为：
根据用户器械和训练部位筛选动作
→ 随机或 shuffle 组合
→ 生成训练计划
营养部分主要基于 Mifflin-St Jeor 和固定宏量分配。
这种方案能够生成可运行的计划，但还不够体现高级个性化。
5.2 训练计划生成器应补充的输入
用户档案需要增加：
年龄；
生理性别；
身高、体重和体脂；
训练目标；
训练经验；
每周可训练天数；
每次可训练时长；
可用器械；
喜欢和不喜欢的动作；
动作熟练度；
伤病和疼痛部位；
当前训练计划；
近期训练量；
近期 RPE/RIR；
睡眠和疲劳；
主要动作表现；
计划执行率。
5.3 建立训练模板系统
不要让 Agent 从动作库完全自由拼装。
建议先建立经过校验的训练模板：
全身训练 2日
全身训练 3日
上下肢 4日
推拉腿 3日
推拉腿 6日
力量型 3日
增肌型 4日
减脂保肌型 4日
Agent 的任务是：
选择最合适的模板；
根据器械和伤病替换动作；
调整组数、次数和强度；
对计划执行约束检查。
5.4 建立训练约束校验器
计划生成后必须由代码检查：
每周训练次数是否符合要求；
单次时间是否超限；
动作是否使用了不可用器械；
是否包含禁用动作；
同一肌群恢复时间是否合理；
每周肌群组数是否在允许范围；
训练量是否突然大幅增加；
动作模式是否均衡；
是否缺少热身、休息和替代方案；
新手计划是否出现过高复杂度。
硬约束必须达到 100% 满足。
5.5 增加渐进负荷机制
计划不能只记录动作、组数和次数，还应包含：
目标重量
目标 RPE 或 RIR
递增规则
未完成时的回退规则
减量周规则
动作替换条件
例如：
若所有工作组均达到目标次数且 RIR ≥ 2：
下次上肢动作增加 2.5 kg

若连续两次无法达到最低次数：
降低重量 5%，重新累积
这些规则应由程序执行，而不是每次由 LLM 临时决定。
6. 核心不足四：膳食计划目前更接近“营养框架”
6.1 当前问题
当前可以计算 TDEE 和宏量营养目标，但尚未看到完整的：
每日具体餐食；
食材克数优化；
训练日与休息日差异；
食谱替换；
预算约束；
烹饪时间约束；
购物清单；
过敏强校验；
营养误差自动收敛。
6.2 改进方案
建立三层膳食生成结构：
第一层：营养目标计算
由确定性程序生成：
每日热量
蛋白质
碳水
脂肪
膳食纤维
训练日营养
休息日营养
训练前后餐目标
第二层：餐次分配
根据用户训练时间生成：
早餐
午餐
训练前餐
训练后餐
晚餐
加餐
第三层：食材组合优化
使用约束优化算法，不要让 LLM 直接猜克数。
可以采用：
OR-Tools；
scipy.optimize；
PuLP。
优化目标：
最小化热量误差
+ 蛋白质误差
+ 碳水误差
+ 脂肪误差
+ 食材成本
+ 用户不喜欢程度
+ 食谱重复度
约束包括：
过敏食材必须为 0；
用户忌口不得出现；
热量误差不超过阈值；
蛋白质达到最低要求；
每餐食材重量处于合理范围；
总成本不超过预算；
烹饪时间不超过限制。
6.3 食谱替换机制
用户点击“换一道”时，不应重新生成整日计划。
应执行：
锁定其他餐食
→ 计算当前剩余宏量
→ 搜索同类食物
→ 优化替换克数
→ 校验全天营养
→ 生成局部变更
7. 核心不足五：缺少训练与饮食的动态联合调整
README 已将“周计划自动调整”列为后续功能。
但动态调整实际上是 FitPilot 区别于普通健身计划生成器的核心能力，应提高优先级。
7.1 每周联合分析输入
每周分析至少读取：
体重趋势；
体脂趋势；
腰围趋势；
训练完成率；
饮食完成率；
主要动作表现；
训练容量变化；
RPE/RIR；
睡眠；
疲劳；
疼痛；
用户主观反馈。
7.2 调整决策应先诊断原因
例如体重停止下降时，应区分：
饮食执行率低
记录数据缺失
真实热量摄入偏高
身体短期水分变化
训练活动量下降
确实需要降低热量
不能看到体重停滞就直接减少热量。
7.3 调整规则示例
体重下降过快且力量下降
提高训练日碳水；
适当提高总热量；
保留主要动作强度；
降低部分辅助训练量；
观察下一周期。
体重停滞但执行率低
不降低热量；
优化食谱难度；
减少烹饪复杂度；
增加外食替代方案；
改善记录完整度。
恢复良好且训练轻松
小幅提高训练量或重量；
保持饮食计划；
不同时大幅增加多个变量。
每次调整必须保存：
调整前数据
诊断结果
调整内容
调整原因
调整前后差异
用户确认
新计划版本
8. 核心不足六：RAG 入库与切分仍是基础版本
8.1 当前问题
当前切分主要是：
标题优先
约 900 字
重叠 120 字
这种方案能够运行，但对长篇指南、表格、动作说明和营养标准还不够精细。
8.2 按文档类型切分
指南和教材
文档
→ 章节
→ 小节
→ 语义段落
动作说明
一个完整动作块尽量包含：
动作名称
目标肌群
辅助肌群
器械
准备姿势
执行过程
常见错误
注意事项
替代动作
食谱
食材、用量、步骤和营养信息不能被拆开。
表格
应按表头和数据行重构为结构化文本，不能直接把整张表按字符切断。
8.3 增加 Parent-Child 检索
建议建立：
Parent Chunk：完整章节或完整动作说明
Child Chunk：较小的精准检索片段
检索 Child，返回 Parent 或相邻 Child，使系统兼顾：
精准召回；
完整上下文；
引用可读性。
建议初始范围：
Child：200～500 tokens
Parent：800～1500 tokens
最终值应通过评测确定。
8.4 完整元数据
每个 Chunk 至少保存：
document_id
document_version
chunk_id
parent_id
title
section_path
page_number
source_url
source_type
language
topic
applicable_goal
applicable_population
risk_tags
evidence_level
published_at
content_hash
parser_version
chunk_strategy_version
embedding_model_version
access_scope
9. 核心不足七：Query 改写和多路查询尚未完整落地
README 当前检索链路是：
query
→ Dense + BM25
→ RRF
→ Reranker
但复杂多轮问题需要增加 Query Understanding。
9.1 增加历史感知改写
例如用户说：
那休息日呢？
系统需要结合前文改写为：
在减脂并保持力量目标下，休息日的热量和碳水如何安排？
改写时必须保留：
数字；
否定词；
训练目标；
时间范围；
食物和动作实体；
用户约束。
9.2 多路查询应按需启用
不要所有问题都启用 Multi-Query。
建议：
简单事实查询：直接检索
同义表达较多：Multi-Query
短问题、长答案：实验 HyDE
复杂问题：任务分解式查询
个人数据查询：直接查数据库，不使用 HyDE
需要记录：
original_query
rewritten_query
query_variants
rewrite_reason
entities
constraints
10. 核心不足八：拒答策略不能只依赖单个分数阈值
当前 build_context 会在证据少或分数低时拒答。
这个方向正确，但仅依赖相似度阈值会出现：
有相似文档但不能支持答案；
没有直接证据却被高相似度文本误导；
需要用户数据但用户没有填写；
工具失败后模型仍继续回答；
多个来源互相冲突。
10.1 拒答类型应细分
knowledge_not_found
insufficient_user_data
tool_execution_failed
conflicting_evidence
out_of_scope
medical_or_high_risk
permission_denied
10.2 多信号判断
综合：
Top-1 分数；
Top-k 分数分布；
Rerank 分数；
Dense 与 BM25 是否一致；
是否存在直接支持结论的证据；
是否缺少必要用户数据；
是否有冲突来源；
安全规则；
Answerability 分类器。
10.3 单独评估拒答
必须建立无答案测试集，评价：
No-answer Precision
No-answer Recall
False Answer Rate
Unsupported Claim Rate
Unsafe Answer Rate
11. 核心不足九：引用评价过于简单
当前评估包含 citation_rate，但“回答带了引用”不等于“引用正确”。
应增加：
Citation Precision
引用内容是否真正支持对应结论。
Citation Coverage
回答中的关键事实有多少获得证据支持。
Citation Completeness
引用是否包含：
文档标题；
章节；
页码；
来源 URL；
文档版本；
对应原文片段。
同时需要区分：
知识依据
用户数据依据
计算工具依据
Agent 推断
例如“蛋白质摄入应优先保证”可以引用知识文档；“你的训练日增加 25 克碳水”属于根据用户数据计算的结果，不应伪装成文献原话。
12. 核心不足十：评估体系覆盖不足
当前主要评估：
Hit@K；
MRR；
Citation Rate；
延迟。
这只能证明 RAG 基本可用，无法证明整个 Agent 正确。
需要建立七层评估体系。
12.1 文档解析
解析成功率；
表格数值正确率；
标题保留率；
空文档率；
OCR 异常率。
12.2 RAG 检索
Recall@5；
MRR；
NDCG@5；
Precision@5；
Context Recall；
Context Precision。
12.3 生成与引用
Faithfulness；

17. BM25 本地索引需要重新评估
当前 BM25 是本地文件索引。单实例开发没有问题，但多实例生产会出现：
每个实例索引不一致；
重建过程中查询结果变化；
新实例启动需要完整加载；
无法集中管理；
容器删除后索引可能丢失。
可选方案：
方案 A：保留本地 BM25
适合单机部署，但必须增加：
索引版本；
文件锁；
原子替换；
持久化 Volume；
启动校验；
自动重建；
多实例禁用。
方案 B：使用 Qdrant Sparse Vector
将 Dense 和 Sparse 都交给 Qdrant，简化部署和一致性管理。
方案 C：使用 OpenSearch/Elasticsearch
适合后期知识规模和检索需求明显增长时使用。
当前项目优先建议方案 B。

23. 最终结论
FitPilot 当前最大的优势是：
系统架构方向正确，结构化业务、RAG、Agent、确认写入、确定性计算和基础工程设施已经形成统一项目。
当前最大的不足不是“功能太少”，而是：
很多能力仍停留在可演示基线，没有达到可恢复、可验证、可审计、可长期运行的生产工程标准。
下一阶段不建议继续快速增加页面、工具数量或复杂模型，而应优先完成四条主线：
Agent 持久化和任务可靠性；
训练—饮食联合计划的确定性约束与动态调整；
RAG 数据治理、引用、拒答和完整评测；
生产部署、安全、日志、备份和审计。
完成 P0 和主要 P1 后，FitPilot 才能从“功能完整的健身 AI Demo”升级为：
可持续运行、可复现决策、可验证质量、可安全修改用户计划的个性化训练与膳食协同 Agent。
